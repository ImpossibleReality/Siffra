# Conformance Checks

> Disclaimer: This crate was fully generated by AI--it was a sanity check on my end to make sure
> that I implemented my dimensional analysis correctly.

Cross-checks **every unit siffra knows** against an independent reference implementation of unit
conversion: **GNU units** (`units(1)`).

It looks for `gunits`, then a plain `units` on `PATH` _if_ it is GNU units; a non-GNU `units` (such
as the BSD one on macOS) is rejected. Override the binary with `CONFORMANCE_UNITS=<path>`.

It is a developer tool, not part of the shipped product.

## Run it

```sh
cargo run -p conformance              # full report, grouped by category
cargo run -p conformance -- --fails-only   # only the rows needing attention
cargo test -p conformance             # regression guard (skips if `units` absent)
```

The binary exits non-zero if any unit disagrees with the reference beyond a small convention-level
tolerance, so it works as a CI gate.

## How it works

Every unit is enumerated straight from `siffra::catalog::catalog()`, so a unit added to the engine
is picked up here automatically — no list to maintain.

For each unit, siffra's own definition gives the value of **one** of it in a fixed set of canonical
base units:

```
meter · second · gram · mole · radian · kelvin · bit · ampere
```

(read directly off the enums via `Unit::factor`, so no formatted output is re-parsed). The reference
tool is then asked to convert `1 <unit>` into the matching base-unit string, and the two magnitudes
are compared.

Three shapes are handled specially:

- **Affine temperatures** (`°C`, `°F`, …) — an offset, not a ratio — are compared at several anchor
  points via GNU units' `tempC(x)` functions (the bare `degC` unit is only a 1 K interval).
- **Dimensionless scalars** (`%`, `ppm`, …) are checked against their exact definition (exact by
  construction, and independent of the tool).
- **Currencies** are skipped (a live exchange rate is not a fixed conversion).

## Reading the report

| status     | meaning                                                            |
| ---------- | ------------------------------------------------------------------ |
| `ok`       | agrees with the reference to ≤ 1e-9 relative error                 |
| `≈ close`  | sub-tolerance (≤ 1e-3) difference — a definitional nuance          |
| `≠ known`  | a documented convention split where siffra is deliberately correct |
| `MISMATCH` | disagreement beyond tolerance — **needs review** (fails the test)  |
| `no ref`   | the reference tool has no name for this unit                       |
| `skipped`  | not checked (currency)                                             |

Only `MISMATCH` fails `cargo test`. The `≈ close` and `≠ known` rows are reference-side convention
differences, not siffra bugs — for example:

- **Mach**: temperature-dependent — siffra uses 340.29 m/s (15 °C), the reference 331.46 m/s (0 °C).
- **calorie**: siffra uses the thermochemical calorie (4.184 J); the reference the IT calorie
  (4.1868 J).
- **year / month / …**: siffra uses the Julian year (365.25 d).

Documented splits live in `known_difference()` in `src/lib.rs`. Add to it when a new one is
confirmed to be a reference quirk rather than a siffra error.
